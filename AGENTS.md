# AGENTS.md — TAK Codex Working Agreement

You are coding on **TAK**, a Google Sheets-backed project/task manager with a local standalone demo. The goal of this workstream is **exceptional usability, design consistency and speed**, not feature expansion for its own sake.

1. `docs/PRODUCT_REQUIREMENTS_MVP.md` — approved MVP product scope and acceptance.
2. `docs/UI_UX_DESIGN_SPEC.md` — authoritative interaction and visual contract.

6. Existing `readme.md`, `ProductRequiremtns.md`, and `IMPLEMENTATION_PLAN.md` for existing behavior and long-term context. Do **not** pull deferred features into the MVP from these older documents.
7. For anything that versions, tags, pushes to Apps Script or releases: `docs/RELEASE.md` and the **Release and deployment gate** section below.

In case of conflict: **data safety > MVP functional requirements > UX details > implementation suggestions**. Surface unresolved design/functional conflicts in your report. Do not expand scope silently.

## Non-negotiable boundaries

- **Do not implement agentic task workflows in this MVP.** Codex is the *developer*, not a task runner integrated into the product. No claim APIs, autonomous agents, stale claims or orchestration UI.
- Preserve **both** working modes: standalone static/local browser (`localStorage`) and Apps Script web app (Google Sheets). They must never misleadingly claim to synchronize with each other.
- Preserve existing user data, IDs, parent/dependency validation, ordering semantics, conflict safety, CSV export and existing Gantt functionality. Avoid schema migrations unless specifically authorized with backup, test and rollback.
- Prefer incremental changes to current dependency-free HTML/CSS/JS and shared `Core.js`. **Do not introduce React, Next.js, a database, bundler, UI component framework or state-management library without an explicit trade-off review and approval.**
- Never modify production spreadsheets, run `setupTracker` on production, publish a deployment, execute `clasp push`, force-push, or merge/push branches without explicit approval. Verify the target Apps Script project, spreadsheet and environment for any approved deploy.
- Do not commit credentials, tokens, private Sheet IDs, `.clasp` secrets or user data to docs, test fixtures or source control.
- No hand-edits to build-owned output where regeneration is required. `CoreScript.html`, `Version.js` and `dist/index.html` are generated by `npm run build`; update source (or the version in `package.json`) and rebuild. Review tracked generated diffs.

## Required coding loop

For every small work item:

1. **Inspect** source and existing tests; state actual behavior, risks, and affected files.
2. **Plan** a reviewable change with explicit acceptance criteria and scope exclusions.
3. **Implement** only the agreed slice. Prefer direct, coherent code over speculative abstractions.
4. **Verify** with `npm run check` and relevant interaction tests where available, preferably run locally by the user to conserve Codex usage. Test both modes when the change touches persistence or build/runtime differences. If the environment cannot run a test, report that plainly; do not claim it passed.
5. **Report** changes, screenshots/measurements when useful, regressions checked, current limitations and next slice. Do not mark an item done on visual plausibility alone.

Do not bundle visual redesign, data migration, backend write-path refactor and new features into one unreviewable change.

## Codex-efficient Playwright policy

- Prefer local, human-run Playwright execution in VS Code PowerShell. Codex writes/maintains tests and diagnoses failures; do **not** launch full browser suites, interactive browser sessions, or repeated screenshot/trace inspections unless explicitly requested.
- After each small change, specify the exact targeted test command for the user to run. The user shares only failing test names, concise errors and selected diagnostics; do not ingest complete successful logs, HTML reports or trace archives into model context.
- Preserve existing Playwright projects, tests and configuration. Do not add dependencies or modify test infrastructure without approval. Recommend concise console + HTML reporting, failure-only screenshots/traces and video disabled, but verify the current config before changing it.
- Local test execution is not equivalent to testing the Google Sheets/Apps Script mode. Record what was and was not verified.
- See `TESTING.md` for local commands and the manual test/fix loop.

## UX quality rules

- Minimal visual appearance + balanced discoverability; keyboard and mouse must both be efficient.
- **Title-only fast creation**; common properties directly editable; advanced fields in details panel.
- Preserve useful focus, selection, filter and scroll state across routine changes.
- Use design tokens and accessible semantic colors; no pervasive tiny text, inconsistent random colors or duplicate navigation.
- Dialogs must trap/restore focus, support Escape appropriately and preserve unsaved drafts.
- Avoid hover-only functionality; provide keyboard/touch alternatives, feedback and accessible labels.
- Maintain existing shortcuts `N`, `/`, `1`, `2`, `3`, `Esc`; handle typing fields, IME composition and modifier keys correctly. Add others only without conflict.

## Speed and persistence rules

- Treat smooth animations as **not a substitute for speed**. Measure under defined conditions, including a 2,000-task dataset.
- Targets: local feedback p95 <100 ms; loaded-view navigation p95 <150 ms; initial usable view target <3s; typical Apps Script save target <2s under documented conditions. These are goals requiring evidence, not current guarantees.
- Display accurate **Pending/Saving, Saved, Failed, Conflict** states. A local optimistic update is not a successful server save.
- A rejected or timed-out inline edit must retain the user's draft for retry/copy/conflict resolution. Do not silently overwrite newer remote data.
- Use safe mutation ordering, targeted rendering and debouncing where justified. Retain correct behavior on failed requests, long latency and quick successive edits.

## Phase/release gates

- Phase 0: baseline report, risk map, branch and test plan; **no code changes** until approved.
- Subsequent phases: small PR/commit series with acceptance checks from the plan.
- Stop and request approval before adding new dependencies, altering the Sheets schema, expanding product scope, changing authentication/sharing or deploying to production (see **Release and deployment gate**).

## Release and deployment gate

> **Never move a production deployment, and never create a new Apps Script version or deployment, on your own initiative.** Production changes only after the owner has tested on `/dev` and approved in writing. The full steps are in `docs/RELEASE.md`; this section is the rule that governs them.

Targets: the **shared host** (`USER_ACCESSING`, one `/exec` for all users), the **starter template** (new copies only) and **independent installs**. They are released separately and in that order; the template embeds the host's verified `/exec` URL.

```text
[ Local change + version + release notes + tag ]
        |
        v  owner approves a /dev push for a named target project
[ clasp push -f  ->  Dev draft (@HEAD, /dev) ]
        |
        v  STOP. Give the owner the /dev URL pattern and what to test. Wait.
        |
        v  owner writes "approved", "deploy to prod" or equivalent
[ clasp version "vX.Y.Z - notes"  ->  clasp deploy -i <ID> -V <N> -d "vX.Y.Z - notes" ]
        |
        v  verify the real /exec on a test copy; report it
```

**What an agent may do without asking:** change source and tests, set the version in `package.json`, run `npm run build` and `npm run check`, write release notes, stage a package with `node scripts/stage-package.mjs`, and commit locally. Pushing the Git branch and tag still needs approval, as above.

**Phase 1 — dev push (needs approval for that push).** Name the target Apps Script project and confirm it is the intended one before pushing. For the shared host and the template, run `clasp` only from the staged `.release/<target>` folder, never from the repository root (the root has no `SharedConfig.js` and would produce an independent install). Push with `clasp push -f`, then **halt**: report that `@HEAD` changed, give the `/dev` URL pattern and a test list, and do not run `clasp version` or `clasp deploy`.

**Phase 2 — production (human-gated only).** Proceed only on explicit written approval given *after* the `/dev` test, for this version. Then: find the production deployment ID with `clasp deployments`, freeze `clasp version "vX.Y.Z - notes"`, move it with `clasp deploy -i <DEPLOYMENT_ID> -V <N> -d "vX.Y.Z - notes"`, and verify the live `/exec` from a private test copy. Never run `clasp deploy` without `-i` (it creates a new `/exec` URL and orphans every template copy). Keep the host deployment `USER_ACCESSING`.

**Versioning.** The version is written in exactly one place, `package.json` (`npm version <patch|minor|major> --no-git-tag-version`). The build generates `Version.js` and the header badge. Add the version to `docs/RELEASE_NOTES.md` (table row and entry) in the same change. Use one `vX.Y.Z` for the Git tag, Apps Script version description and deployment description. Do not edit `docs/RELEASE.md` examples when releasing.

**Scripts.** `npm run release` performs the production steps and is for a person at an interactive terminal; it refuses CI and non-interactive runs. **An agent must never run it.** `npm run clasp:info` is read-only but still runs `clasp`, so it needs the same approval as any other `clasp` command.

**Never commit** script IDs, deployment IDs, spreadsheet IDs, the shared `/exec` URL, tokens or `.clasprc.json`. Use placeholders in docs. The repository's `.clasp.json` is the maintainer's; do not rely on it for the host or template.

**Rollback** is re-pointing the deployment to the last good version (`clasp deploy -i <ID> -V <GOOD_N>`), after the owner agrees. Do not delete users' spreadsheets or rows.
